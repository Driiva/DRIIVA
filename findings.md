## Logic-gap harness — runtime defect register (2026-06-26)
> 80 agents, 3-lens evidence-grounded verify. **3 CRITICAL / 11 HIGH / 9 MEDIUM / 1 LOW** (24 confirmed, 1 refuted of 27 raw). These are PRE-EXISTING runtime defects (not introduced by the marketing/Phase-1 branch). Full report archived in the workflow transcript.

**Executive summary.** Driiva has three release-blocking defects that each break a core promise of an insurtech: (1) WebAuthn passkey enrolment is unauthenticated, so anyone who knows a user's email can bind their own authenticator and take over the account; (2) the Stripe webhook returns 200 before it does any work and only console.errors failures, so a charged customer can end up with no bound policy and zero retry — a money-in/no-cover state; and (3) endTrip writes score/events fields the Firestore rules forbid, so every non-trivial trip is rejected, stuck in 'recording', and never scored — the telematics product does not actually function end to end. Beneath these, the same root causes repeat: authoritative values (premium, price, score) are computed on the client instead of the server, two data stores (Firestore vs Postgres) drift with no reconciliation, multi-write operations have no transaction, and detection logic (fraud anomalies, input validation) is computed but never enforced. Fix the three CRITICALs first, then close the pricing-authority and dual-store split-brain clusters before any paid go-live.

### Themes
- Client-side authority over money and risk: premium, Stripe priceId, and driving score are computed/trusted client-side when only the server (Root Platform, Cloud Functions) should be authoritative — enabling price tampering, premium drift, and score forgery.
- Dual-store split-brain with no reconciliation: Firestore and Postgres (and trip-row vs profile/leaderboard aggregates) are written as independent, non-transactional operations, so any partial failure leaves the two stores permanently disagreeing.
- Fire-and-forget error handling: catches that only console.log/error (Stripe webhook, onboarding PATCH, Firestore write) silently drop side effects with no retry, rollback, or persisted intent — failures are invisible to ops and user alike.
- Detection without enforcement: anomaly/duplicate/impossible-speed detection and input validation are computed but never block — the boundary exists at the scoring/HTML-attribute layer but not at the persistence/submit layer.
- Missing atomicity across multi-step writes: startTrip, endTrip, trip+profile+leaderboard, and the TripPointStreamer flush all span multiple writes with no batch/transaction/in-flight guard, producing orphaned, stuck, or silently-lost data.
- Security boundaries declared but inert: passkey enrolment ungated, sanitizeInput mounted before body parsers (dead code), and rate limiters keyed on req.ip with trust proxy unset (one global bucket behind Vercel/Cloudflare) — controls that look present but do nothing.
- Non-determinism and hardcoded-neutral stubs in the scoring pipeline: Math.random() weather feeds premium, phonePickupCount is never wired (10% weight pinned to max), and boundary-crossing trips vanish from aggregates — the risk model looks weighted but is partly fictional and non-reproducible.

### Confirmed findings
- **[CRITICAL] WebAuthn passkey registration is public — enrol a passkey on any account by email = full account takeover** · `server/routes.ts:178 and server/routes.ts:191 (register/start, register/complete); flows into server/webauthn.ts:139-185` · missing: There is no requireAuth (or any proof of email ownership / existing session) gating passkey enrolment. generateRegistrationOptions/verifyRegistration look the user up purely by the email in the request body, store the challenge under reg_<email>, and on success INSERT a new active credential for that user. An attacker submits victim@email to register/start, completes with their OWN authenticator, and a credential is bound to the victim's account. They then call authenticate/start+complete and verifyAuthentication issues a Firebase custom token for user.firebaseUid (webauthn.ts:276), giving them a real logged-in session as the victim. · fix: Put requireAuth on /register/start and /register/complete and force email = the authenticated user's email (req.auth.email / DB lookup), never the body. First-time enrolment must follow a verified login, not a bare email.
- **[CRITICAL] Stripe webhook ACKs 200 before processing and swallows handler errors — failed policy bind is lost forever (no retry)** · `server/routes.ts:1038 (res.json before work) and server/routes.ts:1082-1084 (catch logs only)` · missing: res.json({received:true}) is sent BEFORE handleStripePaymentSucceeded runs, and the async block's catch only console.errors. Once Stripe has a 200 it never redelivers. So if the Firestore pendingPayment write / Root bind throws (Admin not initialised, Firestore down, transient error), the payment is taken but the policy-bind side effect is permanently dropped with no retry and no persisted intent. · fix: Persist the raw event (e.g. a processed_stripe_events / outbox row) inside the request, return 200 only after that durable write, and process via a retryable worker; OR move processing before the ACK and return non-2xx on failure so Stripe retries. Do not fire-and-forget after responding.
- **[CRITICAL] endTrip writes rule-locked fields (score/scoreBreakdown/events) → every real trip end is permission-denied and never completes** · `client/src/lib/tripService.ts:320-329 (vs firestore.rules:135-145)` · missing: endTrip's batch.update sends score, scoreBreakdown and events with their final values, but the security rule only permits a client recording→processing transition when score/scoreBreakdown/events/anomalies/context are unchanged(). The client path is supposed to flip status ONLY and let the onTripStatusChange Cloud Function compute the score (as firestore.ts:837-847 documents). Writing the score client-side is the step that should not be here. · fix: Remove score, scoreBreakdown and events from endTrip's batch.update(tripRef,...) — only write endedAt, endLocation, distanceMeters, status:'processing', pointsCount, and let the Cloud Function set the scoring fields.
- **[HIGH] Worker crash leaves trip-processing promises hung forever and leaks the pending map** · `server/lib/telematics.ts:654-655 (and pending map at 640, 675-678)` · missing: On the worker 'error' and 'exit' events the code only sets this.worker = null. It never rejects (or re-runs on the main thread) the in-flight entries still sitting in this.pending. The fallback to super.processTrip only runs at getWorker() time, never for a request already dispatched to the worker. · fix: In both the 'error' and 'exit' handlers, iterate this.pending, reject each entry (or retry via super.processTrip), then clear the map; also add a per-request timeout that rejects and falls back to main-thread processing.
- **[HIGH] Documented Stripe webhook handlers are stubs — cancellation and payment failure never update policy state** · `server/routes.ts:1061-1068 (invoice.payment_failed), 1069-1073 (customer.subscription.deleted), 1074-1078 (checkout.session.completed)` · missing: The header comment promises 'subscription.deleted → mark policy cancelled', 'payment_failed → notify user', 'checkout.session.completed → handle one-time purchases', but all three branches only console.log. A user who cancels their subscription (or whose renewal fails) has no corresponding cancellation/cover-lapse recorded; the policy stays active in the app's view. · fix: Implement the three handlers: on subscription.deleted mark policy/subscription cancelled in the store + Root; on payment_failed flag past_due and notify; on checkout.session.completed fulfil the add-on. Or remove the misleading comment until wired.
- **[HIGH] Trip insert, profile update and leaderboard update are three separate writes with no transaction** · `server/routes.ts:368-405 (createTrip 368, updateDrivingProfile 391, updateLeaderboard 403); no db.transaction exists anywhere in server/` · missing: There is no transaction boundary wrapping the trip persistence and the derived profile/leaderboard mutations. If updateDrivingProfile or updateLeaderboard throws after createTrip succeeds, the trip row is already committed but the profile's currentScore/totalTrips/totalMiles never absorb it. · fix: Wrap createTrip + updateDrivingProfile + updateLeaderboard in a single db.transaction so the trip and its aggregates commit or roll back together.

- **[HIGH] Onboarding flag written to two stores that can permanently disagree; Postgres PATCH failure silently bounces the user back into onboarding** · `client/src/pages/quick-onboarding.tsx:178-191 (PATCH) + 193-216 (Firestore) ; consumed AuthContext.tsx:131-139 (fast path Firestore) vs 181-189 (slow path Postgres)` · missing: handleComplete fires the PATCH /api/profile/me (Postgres) and the Firestore setDoc as two independent writes. The PATCH is wrapped in a try/catch that only console.errors on failure (lines 188-190), then the code unconditionally proceeds to write Firestore onboardingComplete:true and advance. There is no check that the PATCH succeeded, no rollback of the Firestore write, no retry. AuthContext's fast path reads onboardingComplete from Firestore (true) but the background slow path overwrites it with the Postgres value (profile.onboardingComplete === true, line 187). If the PATCH failed, Postgres stays false: on the next session the user is shown the dashboard then yanked back into onboarding mid-session. · fix: Await the PATCH, check res.ok, and only write Firestore + advance when the server write succeeded; surface a toast and keep the user on the confirm step on failure (single source of truth or a server-side reconcile).

Every per-IP limiter (authLimiter 10/min, gdprDeleteLimiter 3/hr, apiLimiter) therefore shares a single global counter keyed on the proxy IP rather than the caller. · fix: Set app.set('trust proxy', 1) (or the correct hop count) in server/app.ts and derive the client IP from the trusted X-Forwarded-For, or key sensitive limiters on authenticated uid where available.

The whole point is each user pays their individually-computed premium, but the client can substitute any Price object that exists in the Stripe account. · fix: Server-side allow-list the acceptable priceId(s) (or always derive price from the server-computed premium); reject any priceId not in the known set.

Separately, checkout computes discountPct as (score-50)*0.6 and scoring.ts uses yet another refund formula — no shared source of truth. · fix: Make scoreFactor return 1 - ((clamped-75)/25)*0.15 to honour ±15%, and centralise one discount/score function used by pricingEngine, checkout and scoring.
